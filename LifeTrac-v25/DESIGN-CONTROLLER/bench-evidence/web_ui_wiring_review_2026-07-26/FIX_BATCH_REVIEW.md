## Lens: concurrency

Concurrency review of the uncommitted batch. The batch's core lock discipline is mostly sound: _set_pending/_next_ctrl_body/_clear_pending and the new pump gate all take self._lock with no nesting (no deadlock possible); the tractor's _enc_ack_out swap is now correctly atomic; web_ui's _set_runtime_encode_mode_override updates both fields under one lock and all _radio_profile_active writes (including the new paho-thread capture) are under _radio_profile_lock; wait_for_publish inside asyncio.to_thread is safe (Condition-based, and the rc==SUCCESS guard prevents is_published's raising paths); camera_service's WEBP_QUALITY paho-thread write is a GIL-atomic int rebind (worst case one frame encodes with new mode + old quality — benign). Air-verified invariants held: RS-4.12 re-arm ordering is preserved on every changed TX path, the tractor's two-phase profile switch still flushes the 0x66 ack on the old grid before switching even for mid-burst-dispatched commands, the RX worker remains the sole HostLink owner (MQTT callbacks only touch lock-guarded state), and the LIFETRAC_KF_REQUEST_DISABLE choke point is untouched. Seven real findings: (1) the new 0x68 ack-match compares mode only, so an in-flight ack for the OLD quality clears a pending same-mode/new-quality command (RS-1.5 convergence regression for the new quality feature); (2) the ack-clear path drops self._lock between reading the pending body and _clear_pending's unconditional pop, so a paho-thread _set_pending landing in that window is silently discarded — recreating the exact superseded-command loss this batch fixes; (3) moving _run_bench_radio_script to asyncio.to_thread removed the accidental event-loop serialization, so two concurrent bench POSTs now race two helper subprocesses over the same serial hardware; (4) the 600 s retained-pin stale gate removes the daemon-restart convergence path — an RX daemon restarting >10 min after the last pin boots on its env default and splits the grid; (5) _enc_ack_last_fwd is read on the paho thread but written unsynchronized on the TX worker — torn reads impossible under the GIL, worst case a duplicate idempotent 0x68 (benign, per the lens question); (6) the v2 fragment loop's rx_sink harvest is skipped on wait_for_tx_done exception paths, so commands captured during a timed-out/refused TX are still dropped (incomplete fix, not a regression); (7) the lazy auto-policy seed races the broker's retained replay at boot — a slow broker seeds the policy from the module default the fix was meant to avoid. Frontend/app.js, settings.html, tests, and lora_proto changes match the stated intent; 0x63 wire compat is preserved (old tractors read args[0]; btc4 wire values 4/5 remain accepted by the daemon's EncodeMode-value gate, only the UI catalogue dropped them).
