# v25.0.1 First Release — Packaging Plan & Code Triage (v1.0)

Date: 2026-05-26
Author: Copilot (Claude Opus 4.7)
Scope: Recommendation for how to cut, package, and ship the first
production firmware/software release for the LifeTrac v25 tractor X8 and
base-station X8. Also answers: are the image-compression protocols ready?

---

## 1. TL;DR

- **Do NOT create `TractorCodeV25.0.1/` and `BaseStationCodeV25.0.1/` source trees.** That fights git, breaks all cross-references in the existing `*.md`, and immediately bit-rots the moment the next bug-fix lands.
- **Cut the release the way git is designed for it:** annotated tag `v25.0.1` on the repository's commit that builds clean, plus one new directory `LifeTrac-v25/RELEASE/v25.0.1/` that holds **only release manifests** (Dockerfiles, compose, firmware binaries with checksums, install script, version pins, release notes). Sources stay where they are.
- **Move clearly-orphaned code to `LifeTrac-v25/DESIGN-CONTROLLER/_retired/`** using `git mv` so history is preserved. Move beats delete — reversible, discoverable, greppable.
- The first release is **bench-only**. Regulatory profile is still `BENCH_ONLY_FIXED_915` (profile 0). Call it `v25.0.1-bench` so we can't accidentally treat it as field-legal.
- **Image-compression protocols are partially ready:** the per-tile WebP encoder + the full 7-mode ladder (`full / y_only / btc4_per_tile / btc4_per_frame / mono_g4 / adaptive / motion_only / wireframe`) ship in `camera_service.py` and `web_ui.py`, but the back-channel that actually drives the ladder under airtime pressure (`CMD_ENCODE_MODE` 0x63, `CMD_LINK_PROFILE`, `CMD_ROI_HINT` 0x61) is currently **bypassed** by `LIFETRAC_USE_LORA_BRIDGE=1`. For v25.0.1-bench we ship the static encoder (mode = full WebP at `WEBP_QUALITY=55` plus tile-delta) and gate the adaptive ladder behind v25.0.2. See §6.

## 2. Why not `TractorCodeV25.0.1/` and `BaseStationCodeV25.0.1/` top-level folders

The instinct is right (we need a clear "this is what shipped"), but the implementation pattern would hurt us:

| Cost of duplicated trees | Why it bites |
|---|---|
| Two copies of every file | Bug fixes land in one and the other silently rots. We already see this with `docker-compose.yml`, `docker-compose.video-test.yml`, `docker-compose.video-test.v2.yml`. |
| Cross-references break | `IMAGE_PIPELINE.md`, `LORA_PROTOCOL.md`, etc. all reference `firmware/...` paths. Mass-rewriting them is busywork that creates merge conflicts. |
| `git log` lies | History on the new copy starts at the copy. `git blame` no longer finds the original author/commit. |
| CI doubles | Every test job has to choose which copy to test. The pytest cache under `base_station/.pytest_cache` already exists; spawning a second one wastes runtime. |
| Reviewer confusion | "Which one is real? Both?" is a question every new contributor will ask. |

Git tags + a small release manifest dir give us all of the benefits ("here is exactly what shipped, byte-for-byte reproducible") with none of these costs.

## 3. Recommended release layout

```
LifeTrac-v25/
├── DESIGN-CONTROLLER/             # source of truth (lives here, moves nowhere)
│   ├── base_station/              # base X8 sources
│   ├── firmware/
│   │   ├── common/                # shared lora_proto, etc.
│   │   ├── murata_l072/           # L072 C firmware (one tree, shared by tractor + base)
│   │   ├── tractor_x8/            # tractor X8 sources
│   │   └── _retired/              # NEW. Code we keep for history, not for build.
│   └── ...                        # docs, MASTER_PLAN, etc.
└── RELEASE/                       # NEW top-level dir
    ├── README.md                  # how to reproduce any tagged release
    └── v25.0.1-bench/             # one folder per release tag
        ├── RELEASE_NOTES.md       # what's in it, what's known-bad, regulatory scope
        ├── MANIFEST.json          # exact image tags + git commit SHA + checksums
        ├── tractor/
        │   ├── Dockerfile         # frozen copy (or symlink + commit pin) of the build
        │   ├── docker-compose.yml # frozen tractor compose
        │   ├── env.example        # required LIFETRAC_* env values for the release
        │   └── install.sh         # idempotent installer (adb push, docker compose up)
        ├── base/
        │   ├── Dockerfile
        │   ├── docker-compose.yml
        │   ├── env.example
        │   └── install.sh
        ├── firmware/
        │   ├── murata_l072.elf
        │   ├── murata_l072.bin
        │   ├── murata_l072.sha256
        │   ├── flash.jlink        # frozen JLink script
        │   └── flash.ps1          # frozen Windows flasher
        └── SBOM.json              # software bill of materials (pip freeze, apt list, image digests)
```

### What lives in `RELEASE/v25.0.1-bench/` vs. what stays in `DESIGN-CONTROLLER/`

`RELEASE/<tag>/` is **only artifacts that have to be byte-identical to what shipped**:
- compiled L072 firmware binaries with SHA-256 checksums
- frozen Dockerfile + docker-compose.yml (copied at tag time, never edited)
- `pip freeze` and apt package list (the SBOM)
- the install script that bootstraps a board to the release
- release notes + known-bad list

`DESIGN-CONTROLLER/` keeps the **living source**. Tag `v25.0.1-bench` on a specific git commit is the canonical "give me the source for the release"; the `RELEASE/` dir is the convenience layer for someone who only wants the binaries + a recipe.

### Why one combined `RELEASE/<tag>/` and not separate `TractorRelease` and `BaseRelease`
- They share the same git tag (single commit = single coherent snapshot of tractor + base + shared lora_proto + shared L072 firmware).
- They share the same shared modules (`firmware/common/lora_proto`, `firmware/murata_l072/`). Splitting the release means duplicating those.
- A combined release has one MANIFEST.json so an operator can verify "tractor X8 and base X8 are talking the SAME protocol revision" by reading one file.

## 5. Pre-release checklist (the actual steps to cut v25.0.1-bench)

Numbered so it can be a runbook later.

1. **Code freeze items** — finish the 4 final blockers from `2026-05-26_Image_Over_LoRa_AirLink_Proven_Status_Copilot_v1_0.md`:
   - B1 base power-cycle + visual canvas confirmation.
   - B2 keyframe dwell-cap fix (shrink keyframe payload + stage across dwells).
   - B3 real v4l2 camera swap-in.
   - B4 browser screenshot of live tile pane captured as evidence.
2. **Triage code** per §4. Open a single PR named `v25.0.1-bench: triage` that does only retirement moves + `.gitignore` adds + nothing functional.
3. **Pin everything** — `pip freeze` inside both containers, save as `requirements.lock` (tractor + base separately).
4. **Reproducible builds**:
   - Build tractor image, tag `lifetrac-tractor-x8:v25.0.1-bench`, push to whatever registry (or `docker save | adb push` for the bench).
   - Build base image, tag `lifetrac-v25:v25.0.1-bench`.
   - Build L072 firmware; capture `murata_l072.elf` + `.bin` + `sha256`.
5. **Author `RELEASE/v25.0.1-bench/`** with the directory tree from §3. Each Dockerfile / compose is a copy (not symlink) of the current source at tag time.
6. **Write `RELEASE_NOTES.md`** with three sections:
   - "What's in it" — the strict-path image pipeline, web UI, control bus, regulatory profile 0.
   - "Known-bad / out-of-scope" — see §6 below; field operation; FHSS profile 1; OTA updates (Phase C OTA gap from `2026-05-25_Phase_C_Bringup_Complete_OTA_Gap.md`).
   - "How to install" — links to `tractor/install.sh` and `base/install.sh`.
7. **Generate SBOM** — `pip freeze` + `apt list --installed` from both containers + Docker image digests.
8. **Smoke-test on bench hardware** — power-cycle both X8s, run the install scripts from scratch, watch the web UI render a live frame. Capture screenshot in `RELEASE/v25.0.1-bench/evidence/`.
9. **Git tag** — `git tag -a v25.0.1-bench -m "First bench release"; git push --tags`.
10. **Lock the release dir** — add a `.gitattributes` rule that flags `RELEASE/v25.0.1-bench/` as read-only-by-convention; any later fix becomes `v25.0.2-bench`, not an edit-in-place.

## 6. Are the image-compression protocols ready?

Answering the previous-turn question explicitly.

### Status today (what ships in v25.0.1-bench)
- **Per-tile WebP encoder** in `camera_service.py` — *ready and proven*. Drives the 32×32 tile-delta canvas at `WEBP_QUALITY` (env-clamped to [20,100], default 55, currently 30 in the bench compose). Encoder hash-cache in `image_pipeline/tile_cache.py` skips re-encoding unchanged tiles.
- **`TileDeltaFrame` wire format** (LORA_PROTOCOL.md, opcode under PHY_IMAGE) — *ready*. Reassembled cleanly by `image_rx_daemon.py`; published as `lifetrac/v25/video/tile_delta`; consumed by `canvas_renderer.js`.
- **WebP image fallback path** in `web_ui.py` (`lifetrac/v25/video/canvas` whole-frame topic) — present in code, not used by the strict path today.

### Implemented but NOT exercised in v25.0.1-bench (gated, off-by-default)
The full 7-mode encoder ladder is in code on both sides:

| Mode (wire constant) | `camera_service.py` impl | `web_ui.py` UI choice | Status |
|---|---|---|---|
| `full` (0) | yes — baseline RGB WebP ~26 B/tile | yes | shipping baseline |
| `y_only` (1) | yes — luma WebP, base recolors | yes | implemented, untested at scale |
| `motion_only` (2), `wireframe` (3) | legacy slots, silently clamped to `y_only` at receive | UI hides them | retired-in-place |
| `btc4_per_tile` (4), `btc4_per_frame` (5) | yes | yes | implemented, untested at scale |
| `mono_g4` (6) — 1-bit + Group-4 fax, ~4 B/tile | yes | yes (SAFE floor) | implemented |
| `adaptive` (7) | yes — base-station-driven ROI quality | yes | needs back-channel |

The ladder is driven by `EncodeModeController` on the base side, which emits `CMD_ENCODE_MODE` (opcode 0x63) over the LoRa control channel and `CMD_ROI_HINT` (0x61) for operator-cued regions. **In strict-path bench mode (`LIFETRAC_USE_LORA_BRIDGE=1`) the back-channel reader thread is disabled** (see `camera_service.py` edit `if not USE_LORA_BRIDGE`). So today the tractor encoder is pinned to whatever the env says (`full` WebP) and the ladder logic is dead-stick.

### Research / future modes (NOT in v25.0.1)
Documented in `RESEARCH-CONTROLLER/VIDEO_COMPRESSION/README.md` and `GRAYSCALE_RECOLORIZATION.md`:
- Phase A SSDV (160×120 JPEG / 0.1 Hz, FEC). Useful as a "proof of life" floor; not shipping.
- Phase D keyframe + neural temporal inflate (comma.ai `neural_inflate` / `mask2mask`).
- JPEG XL slideshow.
- AV1 monochrome.

### Recommendation for v25.0.1-bench
- Ship the static encoder: `full` WebP at q55 (or whatever the user picks in `settings.html`) + tile-delta caching.
- Mark the adaptive ladder as **present-but-dormant** in the release notes. Re-enable the back-channel reader thread in `camera_service.py` as the first thing in v25.0.2.
- The encoder ladder code is good — do NOT retire it.

## 7. Direct answers to the user's questions

> Should we make a new folder `TractorCodeV25.0.1` and `BaseStationCodeV25.0.1`?

No. Use a git tag + a `RELEASE/v25.0.1-bench/` manifest directory (one combined, not two). Reasons in §2.

> We'll want to make a clean copy of all the software and firmware for the two devices.

A `git checkout v25.0.1-bench` plus the contents of `RELEASE/v25.0.1-bench/` (Dockerfiles, compose, L072 binary, install.sh, SBOM, notes) **is** that clean copy. The shipped binaries are byte-identical because we save image digests + sha256s in MANIFEST.json.

> How can we plan to pull all this into one place?

Bottom-up: §5 step 4 builds the image artifacts; §5 step 5 collects them under `RELEASE/v25.0.1-bench/`. We don't move source — we collect artifacts.

> How much existing code is good vs old?

Roughly (from §4 file-count estimates):
- **~70 % shipping** — the base_station/, firmware/tractor_x8/, firmware/common/, firmware/murata_l072/ (excluding build artifacts), firmware/x8_lora_bootloader_helper/ (Methods G+H runtime parts).
- **~20 % dev/diagnostic** — bench scripts, HIL harness, recovery scripts. Keep, exclude from container via `.dockerignore`.
- **~10 % retired or orphaned** — H7 dual-core, Opta, handheld MKR, hello-world scaffolds, build artifacts checked in, workspace-root throwaways.

> Should we move some, copy the parts we want, place the rest in a retired folder?

**Move** the retired code to `_retired/` with `git mv` (preserves history; reversible). **Copy** the release artifacts (Dockerfile, compose, env.example) into `RELEASE/v25.0.1-bench/` (so they freeze at tag time). **Do not copy** any source code into the release dir — git already has it under the tag.
